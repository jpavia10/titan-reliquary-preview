## MUS-3-01 — Wholesale `type.issues` set leaves specimen `issue` copies stale → wrong mintage shown (data corruption / wrong numbers)
**File:** `tools/pipeline/apply_changes.py:342` (`set`) + `:416` (`issue_copies`)
**What goes wrong:** `issue_copies()` only matches dotted paths of length ≥ 3 (`issues.N.<leaf>`). A Phase 2 contribution replacing a type's `issues` list wholesale (tier `phase2`, allowed — verified `check_event` passes it) updates the type but never re-syncs any specimen's `issue` copy. The app renders mintage from the specimen copy (`display.mintage_txt(s["issue"])`), so the site shows the old number indefinitely. `integrity.problems()` does not detect the divergence.
**Reproduce:** change file, one line: `{"ts":"…Z","by":"model:x","entity":"type","id":"AT.X.2-groschen","field":"issues","new":[{…,"mintage":12345,…}],"source":"Numista N#1","phase":2,"provenance":{…}}` → `apply_changes.apply_file(f, 'collection', dry_run=True)` reports APPLIED; afterwards type issue mintage = 12345 while specimen C272's copy still reads 29892000 (verified live).
**Fix:** in `set()`, when `ent == "type"` and `path[0] == "issues"`, re-sync affected specimens: extend `issue_copies` to return all specimens of the type when `len(path) == 1`, and replace (not patch) their `issue` copy from the matching type issue.

## MUS-3-02 — Publish install step is non-atomic; crash mid-install empties `data/detail/` (data-loss window)
**File:** `tools/pipeline/publish.py:149-155`
**What goes wrong:** the install step deletes **every** `data/detail/*.json` first, then copies the new ones one by one, then the top-level files one by one. A kill, power loss, or full disk in that window leaves `data/detail/` empty (app shows zero coins) or a torn `index.json`. This contradicts the module docstring's guarantee ("stops with exit code 1 at the first failure, leaving data/ and version.json untouched") — that guarantee only covers pre-install failures.
**Reproduce:** code inspection; the window is seconds long but real (the repo's own history notes scratch builds once filled /tmp — disk pressure is not hypothetical).
**Fix:** build the complete new `data/` tree in a temp dir, then `os.replace()` it over `data/` (or: copy new/changed detail files over the old ones first, then delete only files absent from the new build).

## MUS-3-03 — `owner_answers.py` clobbers an unpublished changes file on a same-minute rerun (data loss)
**File:** `tools/pipeline/owner_answers.py:104-108`
**What goes wrong:** output name is `changes_owner_{stamp}.jsonl` with minute-resolution stamp, opened with `"w"`. If Joseph answers questions, Sebastian runs the tool, Joseph answers more, and Sebastian re-runs within the same minute before `publish.py` runs, the second run silently overwrites the first file — those owner-verified events are lost (the `owner_answers.jsonl` log appends, so the questions look answered while their events are gone).
**Reproduce:** run `python3 tools/pipeline/owner_answers.py A.json` twice in one minute with different answers; only the second file survives in `collection/_incoming/`.
**Fix:** open with `"x"` and fall back to a suffixed name (`…-2.jsonl`) when the file exists, or include seconds in the stamp.

## MUS-3-04 — New valuations never record their spot → portfolio history mis-prices new metal items as spot drifts (wrong numbers, latent)
**File:** `tools/pipeline/apply_changes.py:439-443` (`upsert_valuation`); consumer `tools/pipeline/value_history.py:17-29`
**What goes wrong:** `upsert_valuation` hard-codes `"spot_ag": None, "spot_au": None`. `value_history.items()` splits each item into metal + premium as `premium = est − oz × valuation_spot`, where `valuation_spot` is the global mode (63.50 Ag / 4350 Au from the ledger import). Any metal-bearing item valued after the ledger gets its premium computed against 63.50 regardless of actual spot at valuation time — e.g. a 10 oz melt-valued lot booked at $59.88/oz contributes $562.60 instead of $598.80 to every portfolio-history total, and shows a spurious −$36.20 "premium". The mode heuristic can't recover because the lines carry no spots.
**Reproduce:** code inspection + data check: all 313 valuation lines have `spot=None` except the 24 ledger lines at 63.5 (verified); no post-ledger silver/gold specimens exist yet, so latent until the next silver/gold addition.
**Fix:** in `upsert_valuation`, fill `spot_ag`/`spot_au` from the collection's current board spot (`col` isn't passed — thread the board spot through or read `collection/board.json`); better, make `items()` use each item's own latest valuation spot instead of the global mode.

## 6. Motion Lab (#56) gold-dust study

**Verified constraints:** `js/three.min.js` exists (603,445 bytes, REVISION r128, April 2021). `photos/p1/` holds 222 `.webp` files, all 512×512. `sw.js` precaches `js/three.min.js` (line 15) and cache-firsts `/photos/p1/` (line 155). App honors `prefers-reduced-motion` (app.js lines 1882, 2344, 6718, 6759, 6881).

**MUS-6-01 — Photo → point targets.** For each chosen coin photo: draw 512×512 webp to offscreen canvas at working resolution (72×72 = 5,184 cells), accept cells as particle targets with probability ∝ luminance (bright metal dense, dark background sparse). Reject cells outside inscribed circle. Each particle gets position on coin disc + pixel's own RGB (coin re-forms in true colors); second smaller set tinted gold/silver by average hue reads as "dust." 10–14 showcase coins. Budget ≈ 18–24k particles for coin scene.

**MUS-6-02 — Three scenes + morphing.** Scene A: coin montage (discs in loose spiral). Scene B: world map — 49 country markers (~120 particles each) from compact lat/lng→x/y lookup baked in; dotted-world silhouette ~2k faint background points sampled once from tiny embedded bitmap at build time. Scene C: album page — 8×10 grid of ring targets, ~150 particles each. Every particle stores three target positions (attributes); one `uMix` uniform per transition driven by scroll; vertex shader does `pos = mix(mix(A,B,t1), C, t2)` — all GPU, zero per-frame CPU.

**MUS-6-03 — Shader: custom ShaderMaterial, not PointsMaterial.** r128 PointsMaterial can't do multi-target interpolation, pointer stir, or per-particle color+size. Custom ShaderMaterial on THREE.Points: vertex handles target mixing, size attenuation, pointer stir; fragment draws soft radial sprite (smoothstep falloff), additive blending, depthWrite false. Pointer stir: world-space uniform, radial repulsion + tangential swirl with smooth falloff, `uStir` eases to 0 — no CPU particle state.

**MUS-6-04 — Particle counts per device tier.** Tier by 1.5s probe render at startup (measure, don't guess): High (≥55fps at 40k): 60–80k particles, DPR ≤2. Mid (40–55fps): 24–36k, DPR ≤1.5, smaller sprites. Low (<40fps): 8–12k, DPR 1, stir disabled, crossfade-only. Auto-step-down if fps <40 for 2s. Rationale: ≤10px sprites, 30k additive points fits mid-range Adreno/Mali fragment budget.

**MUS-6-05 — Fallbacks.** No WebGL: static composition — real coin photos crossfading per scroll section with CSS, fully readable. `prefers-reduced-motion`: render each scene's final composed state as still point cloud; scroll crossfades stills, no continuous motion, no stir. Canvas `position:fixed` behind text-first content, `pointer-events:none` except stir layer; every scene captioned.

**MUS-6-06 — Measuring fps.** Lab page only: HUD with rolling 60-frame avg fps, p95 frame time, tier, particle count — from rAF deltas. Mirrors #25 philosophy; gives Joseph the motion speed report.

**MUS-6-07 — Offline/page structure.** One `motion-lab.html` + `motion-lab.js` (vanilla ES6, global THREE from r128), relative path to `../js/three.min.js`; add both to sw.js SHELL_URLS. Photos from cache-first `/photos/p1/`. No new libraries, no build.
